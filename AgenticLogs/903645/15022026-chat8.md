Dado que las lobbies son **estado en memoria** (no DB), no encajan bien en `services/` que por convención wrappea operaciones de base de datos (como hace User.ts con Prisma). Mezclarlos crearía confusión semántica.

**Recomendación: `src/managers/LobbyManager.ts`**

La razón:

| Carpeta | ¿Por qué sí / no? |
|---|---|
| `services/` | No: convención = acceso a DB. Las lobbies son estado volátil en RAM |
| `managers/` | Sí: patrón clásico para singletons con estado en memoria |
| `state/` | Válido, pero menos expresivo sobre las operaciones que expone |
| `game/` | Válido si luego quieres agrupar más lógica de partida aquí |

La estructura quedaría así:

```
src/
├── services/         ← todo lo que toca Prisma/DB
│   └── User.ts
├── managers/         ← estado en memoria, singletons
│   └── LobbyManager.ts
└── ...
```

`LobbyManager` sería un singleton (un `Map` de lobbies indexado por ID) con métodos como `createLobby`, `joinLobby`, `leaveLobby`, `getLobby`, `deleteLobby`, etc. Se instancia una vez al arrancar el servidor y vive mientras el proceso esté activo.

Si en el futuro añades lógica de partida en curso (el estado del tablero en memoria antes de persistirlo), también iría en `managers/` como `GameManager.ts`, manteniendo la separación clara con `services/`.

### 3. ¿Por qué singleton exportado como instancia y no como clase?

Se exporta la **instancia** (`lobbiesManager`), no la clase, para que desde cualquier fichero se importe y use directamente sin tener que llamar a `getInstance()` cada vez:

```typescript
import { lobbiesManager } from "../managers/lobbyManager.js"
lobbiesManager.crearLobby(...)
```

- **Mismo fichero**: más simple, las interfaces son internas al manager

User: como puedo hacer de forma eficiente para en eliminar un jugador de la lobby, quitarlo del vector

GitHub Copilot: Con `filter`, es la forma más idiomática y limpia en TypeScript:

```typescript
abandonarLobby(lobbyId: string, email: string): void {
    const lobby = this.lobbies.get(lobbyId)
    if (!lobby) throw new Error(`Lobby ${lobbyId} no encontrada`)

    lobby.jugadores = lobby.jugadores.filter(j => j.email !== email)
}
```

`filter` devuelve un nuevo array sin el elemento, sin necesidad de buscar el índice manualmente. Es $O(n)$ pero para el tamaño máximo de jugadores en una lobby (típicamente 2-6) es completamente irrelevante.

La alternativa con `splice` sería:

```typescript
const idx = lobby.jugadores.findIndex(j => j.email === email)
if (idx !== -1) lobby.jugadores.splice(idx, 1)
```

`splice` muta el array original (sin crear uno nuevo), lo que es marginalmente más eficiente en memoria, pero la diferencia es despreciable. **`filter` es preferible** por legibilidad.

GitHub Copilot: El `LobbiesManager` no debería saber nada de WebSockets ni de mensajes de cliente. Lo correcto es que el manager devuelva un **objeto de resultado estructurado** y sea la capa de WebSocket/handler la que construya el mensaje para cada cliente.

### Patrón: resultado estructurado

Define un tipo de resultado para la operación:

```typescript
// src/types/lobby.ts
export type LobbyEventResult = {
    expulsado: { email: string }
    resto: { lobbyId: string; emailExpulsado: string; nombreExpulsado: string }
}
```

El manager devuelve los datos necesarios, sin texto:

```typescript
expulsarJugador(lobbyId: string, emailExpulsado: string): LobbyEventResult {
    const lobby = this.lobbies.get(lobbyId)
    if (!lobby) throw new Error(`Lobby ${lobbyId} no encontrada`)

    const jugador = lobby.jugadores.find(j => j.email === emailExpulsado)
    if (!jugador) throw new Error(`Jugador ${emailExpulsado} no está en la lobby`)

    lobby.jugadores = lobby.jugadores.filter(j => j.email !== emailExpulsado)

    return {
        expulsado: { email: emailExpulsado },
        resto: { lobbyId, emailExpulsado, nombreExpulsado: jugador.nombre }
    }
}
```

Y en el handler de WebSocket construyes el mensaje según el destinatario:

```typescript
const resultado = lobbiesManager.expulsarJugador(lobbyId, emailExpulsado)

// Al expulsado
wsDelExpulsado.send(JSON.stringify({
    tipo: "EXPULSADO_LOBBY",
    mensaje: "Has sido expulsado de la lobby"
}))

// Al resto
lobby.jugadores.forEach(j => {
    wsDeJugador.send(JSON.stringify({
        tipo: "JUGADOR_EXPULSADO",
        mensaje: `${resultado.resto.nombreExpulsado} ha sido expulsado`
    }))
})
```

### Por qué esta separación

- El manager solo gestiona **estado** → fácil de testear sin simular WebSockets
- El handler gestiona **comunicación** → puede personalizar mensajes, idioma, formato
- Si mañana añades REST o logs, el manager no cambia

Los strings de error como `"El lobby no existe"` o `"El lobby está lleno"` sí deberían eliminarse. Hay dos estrategias según el tipo de retorno:

**Para errores de validación → `throw` en vez de `return string`**

El handler los captura con `try/catch` y construye el mensaje para el cliente:

```typescript
joinLobby(_idJugador: string, username: string, lobbyID: string) {

    if (!lobby) throw new Error("LOBBY_NOT_FOUND")
    if (lobby.numJugadores >= 4) throw new Error("LOBBY_FULL")
    if (this.jugadoresEnCola.has(_idJugador)) throw new Error("ALREADY_IN_LOBBY")
    // ...
}
```

**Para resultados exitosos que afectan a múltiples clientes → devuelve datos estructurados**

Por ejemplo `deletePlayer` cuando el creador expulsa a alguien:

```typescript
// en vez de no devolver nada o devolver un string
return { expulsado: aEliminar, lobbyId: lobbyID }
```

**En el handler:**

```typescript
try {
    const resultado = lobbyManager.deletePlayer(requestBy, idJugador, lobbyID)
    wsRequestBy.send(JSON.stringify({ tipo: "OK" }))

```

Bien, ya usas `node:test` + `assert`. Para el `LobbyManager` el patrón sería el mismo pero con diferencias importantes dado que es estado en memoria:

**Estructura recomendada:**

1. **Sin `after` de limpieza de DB** — no hay Prisma aquí, pero sí necesitas un `beforeEach` equivalente: resetear la instancia del manager entre tests para que no haya contaminación de estado entre casos.

2. **Agrupa tests por método** con `describe` (disponible en `node:test`) — `createLobby`, `joinLobby`, `deletePlayer`, etc.

3. **Orden de tests importa** — como el manager es un singleton, si no reseteas entre tests, el estado del test anterior afecta al siguiente. Tienes dos opciones:
   - Exponer un método `reset()` en el manager solo para tests
   - Hacer que cada test construya su propio estado desde cero de forma secuencial y predecible

4. **Testa los `throw`** — usa `assert.throws` / `assert.rejects` para verificar que los errores se lanzan con el código correcto (`"LOBBY_NOT_FOUND"`, etc.)

5. **Flujos completos** — además de tests unitarios por método, añade algún test de flujo: crear lobby → unirse → expulsar jugador, para verificar que el estado es consistente al final.

6. **Casos límite clave** para este manager:
