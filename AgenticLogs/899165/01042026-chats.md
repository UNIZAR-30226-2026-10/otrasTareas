El problema principal es que has limitado la altura del contenedor (`Surface`) a un valor muy pequeño (**35.dp**) y, además, estás aplicando un **padding inferior** y un **offset vertical** al icono que desplazan el contenido fuera del área visible.

En Material 3, un `TextField` tiene un padding interno por defecto considerable. Al forzarlo a medir 35.dp de alto y añadirle un `.padding(bottom = 8.dp)`, el espacio real para el texto es casi inexistente, lo que hace que el texto se renderice "fuera" o por debajo del área de recorte de la `Surface`.

Aquí tienes los puntos clave para corregirlo:

### 1. Usa `BasicTextField` para controles pequeños
Si quieres una barra de búsqueda tan delgada (35.dp), el `TextField` estándar de Material 3 no es ideal porque está diseñado para medir al menos 56.dp de alto. Es mejor usar `BasicTextField` para tener control total, o ajustar los `contentPadding` si usas `TextFieldDefaults.DecorationBox`.

### 2. Elimina el desplazamiento manual y el recorte
Si quieres mantener tu estructura actual, haz estos cambios:

```kotlin
Surface(
    color = color_secondary,
    shape = RoundedCornerShape(16.dp),
    border = BorderStroke(2.dp, color_primary),
    modifier = Modifier
        .height(40.dp) // Aumentamos un poco para dar aire (35 es muy justo)
        .width(180.dp)
) {
    TextField(
        value = textState,
        onValueChange = { textState = it },
        leadingIcon = {
            Icon(
                imageVector = Icons.Default.Search,
                contentDescription = "Buscar",

                modifier = Modifier.size(20.dp) // Icono un poco más pequeño
                // ELIMINADO: .offset(y = 6.dp) -> Esto lo empuja hacia abajo y lo oculta
            )
        },
        singleLine = true,
        textStyle = SETextTypes.plano.copy(textAlign = TextAlign.Start),
        colors = TextFieldDefaults.colors(
            focusedContainerColor = Color.Transparent,
            unfocusedContainerColor = Color.Transparent,
            cursorColor = color_text,
            focusedIndicatorColor = Color.Transparent,
            unfocusedIndicatorColor = Color.Transparent
        ),
        modifier = Modifier.fillMaxWidth() 
        // ELIMINADO: .padding(bottom = 8.dp) -> Esto roba espacio al texto
    )
}
```

### ¿Por qué no se veía?
1.  **Altura insuficiente:** El `TextField` de M3 tiene una altura mínima interna. Al meterlo en un contenedor de `35.dp`, el texto queda centrado verticalmente pero se sale de los bordes.
2.  **`drawBehind` y `Offset`:** Al aplicar un `offset(y = 6.dp)` al icono y un `padding(bottom = 8.dp)` al TextField, estás empujando la línea base del texto hacia abajo. Como la `Surface` tiene una forma definida (`RoundedCornerShape`), todo lo que se salga de esos 35.dp se corta (clipping).

### Recomendación de diseño
Si buscas una estética limpia para una búsqueda pequeña, te sugiero este cambio para que la línea de subrayado sea automática y no tengas que dibujarla a mano (que suele dar problemas de alineación):

```kotlin

    leadingIcon = { Icon(Icons.Default.Search, null, modifier = Modifier.size(20.dp)) },
    singleLine = true,
    colors = TextFieldDefaults.colors(
        focusedContainerColor = Color.Transparent,
        unfocusedContainerColor = Color.Transparent,
        // En lugar de dibujar la línea, usa el indicador nativo pero con margen

        unfocusedIndicatorColor = color_text.copy(alpha = 0.5f)

)
```

**Resumen:** Quita el `.padding(bottom = 8.dp)` del TextField y el `.offset(y = 6.dp)` del Icono. Si sigue sin verse, sube la altura de la `Surface` a **40.dp** o **45.dp**.

```kotlin
Surface(
    color = color_secondary,
    shape = RoundedCornerShape(16.dp),
    border = BorderStroke(2.dp, color_primary),
    modifier = Modifier
        .height(40.dp)
        .width(300.dp)
) {
    // Usamos BasicTextField porque NO tiene paddings internos que corten el texto
    androidx.compose.foundation.text.BasicTextField(
        value = textState,
        onValueChange = { textState = it },
        singleLine = true,
        textStyle = SETextTypes.plano.copy(color = color_text),
        modifier = Modifier.fillMaxSize(),
        decorationBox = { innerTextField ->
            // La Row centra el icono y el texto verticalmente dentro de los 40.dp
            Row(
                verticalAlignment = Alignment.CenterVertically,
                modifier = Modifier.padding(horizontal = 12.dp)
            ) {
                Icon(
                    imageVector = Icons.Default.Search,
                    contentDescription = null,
                    tint = color_text,
                    modifier = Modifier.size(20.dp)
                )
                
                Spacer(Modifier.width(8.dp))

                Box(
                    modifier = Modifier
                        .weight(1f)
                        .drawBehind {
                            // Dibujamos la línea de subrayado AQUÍ dentro
                            val strokeWidthPx = 1.dp.toPx()
                            val y = size.height - 4.dp.toPx() 
                            drawLine(
                                color = color_text.copy(alpha = 0.5f),
                                start = Offset(0f, y),
                                end = Offset(size.width - 10.dp.toPx(), y),
                                strokeWidth = strokeWidthPx
                            )
                        }
                ) {
                    // Si no hay texto, puedes poner un texto de ayuda (opcional)
                    if (textState.isEmpty()) {
                        Text("Buscar...", style = SETextTypes.plano, color = color_text.copy(0.5f))
                    }
                    // Esto renderiza el texto que escribes ("sdasd")
                    innerTextField()
                }
            }
        }
    )
}
```

### ¿Por qué esto sí funciona?
1. **La Surface manda:** Mantiene tus 40.dp de alto y el color azul.
2. **BasicTextField es "invisible":** A diferencia del `TextField` normal (que es enorme y se sale de los bordes), el `BasicTextField` solo ocupa el espacio que tú le digas.
3. **Centrado real:** Al usar `Alignment.CenterVertically` dentro de la `Row`, el texto "sdasd" aparecerá justo en el medio de la barra azul, sin cortarse por arriba ni por abajo.

```kotlin
            if (focusState.isFocused) {
                // AQUÍ TU ACCIÓN: Se ejecuta al entrar en el buscador
                println("El usuario va a escribir")
            }
        },
    // ... resto del código (decorationBox, etc)
)
```

### 2. Acción al pulsar "Intro" o "Buscar" en el teclado
Esto es lo más común en buscadores. Debes añadir `keyboardOptions` y `keyboardActions`.

```kotlin
BasicTextField(
    value = textState,
    onValueChange = { textState = it },
    modifier = Modifier.fillMaxSize(),
    // Configura el botón del teclado como una lupa (Search)
    keyboardOptions = KeyboardOptions(
        imeAction = ImeAction.Search 
    ),
    // Define qué pasa al pulsar esa lupa
    keyboardActions = KeyboardActions(
        onSearch = {
            // AQUÍ TU ACCIÓN: Ejecutar la búsqueda
            println("Buscando a: $textState")
            
            // Opcional: Cerrar el teclado o quitar el foco
            // focusManager.clearFocus() 
        }
    ),
    // ... resto del código (decorationBox, etc)
)
```

### 3. Si te refieres a "Seleccionar el texto" (Marcar letras)
Si lo que quieres es detectar cuando el usuario **subraya o selecciona una palabra específica** con el cursor, eso es más complejo y requiere un `TextFieldValue` en lugar de un `String` simple:

dime que partes de esto deberia de ir en un viewmodel?


------

Para que tu código siga las buenas prácticas de Android (**MVVM**), la regla de oro es: **La UI (el Composable) solo debe pintar cosas y avisar de eventos; el ViewModel debe decidir qué se pinta y gestionar los datos.**

Aquí tienes las partes que deberías mover y por qué:

### 1. El Estado de las Listas
Actualmente tienes `listaAmigosBuscada` y `listaAmigosMostrada` en la UI. Si rotas la pantalla o ocurre un cambio de configuración, esos datos podrían perderse o resetearse si no se gestionan bien.

* **A mover:** `listaAmigosBuscada` y la lógica del `if (isEmpty())`.
* **Por qué:** El ViewModel sobrevive a cambios de configuración y mantiene la "verdad" de lo que el usuario está viendo.

### 2. La lógica de negocio (Búsqueda)
La función que llama a `cF.amigosCase.buscarAmigos` no debería lanzarse directamente desde un `scope.launch` en la Cabecera.

* **A mover:** La ejecución de la búsqueda y el manejo del `CoroutineScope`.
* **Por qué:** Usar `viewModelScope` es más seguro que `rememberCoroutineScope` para tareas de datos, ya que si el usuario sale de la pantalla, el ViewModel se asegura de limpiar las peticiones pendientes.

---

### Así quedaría tu estructura profesional:

#### El ViewModel
```kotlin
class AmigosViewModel(private val cF: CaseFacade) : ViewModel() {

    // Lista "maestra" (la que tienes de ejemplo o la que traigas de BD)
    private val listaOriginal = listaAmigosEjemplo 

    // Estado privado que solo el ViewModel modifica
    private var _listaBuscada = mutableStateOf(emptyList<Usuario>())
    
    // Estado público que la UI lee. Aquí aplicamos tu lógica del IF
    val listaAmigosMostrada: List<Usuario>
        get() = if (_listaBuscada.value.isEmpty()) listaOriginal else _listaBuscada.value

    fun buscarAmigos(query: String) {
        viewModelScope.launch {
            if (query.isBlank()) {
                _listaBuscada.value = emptyList()
            } else {
                // Llamada al caso de uso
                val resultado = cF.amigosCase.buscarAmigos(query)
                _listaBuscada.value = resultado
            }
        }
    }
}
```

#### La Screen (Mucho más limpia)
```kotlin
@Composable
fun AmigosScreen(
    SEState: SENavHostController, 
    viewModel: AmigosViewModel // Inyectas el ViewModel aquí
) {
    Column(
        modifier = Modifier.fillMaxSize(),
        horizontalAlignment = Alignment.CenterHorizontally
    ) {
        CabeceraAmigos(
            SEState = SEState,
            // Solo pasamos la función que dispara la acción
            onSearchAction = { query -> viewModel.buscarAmigos(query) }
        )

        // La UI solo observa el resultado final
        ListaAmigos(viewModel.listaAmigosMostrada, viewModel.cF, SEState)
    }
}
```

### Resumen de qué mover:

| Parte | ¿Dónde está ahora? | ¿A dónde va? |
| :--- | :--- | :--- |
| `listaAmigosEjemplo` | Constante global | Propiedad privada del ViewModel |
| `listaAmigosBuscada` | `remember mutableStateOf` | `State` dentro del ViewModel |
| Lógica `if/else` de la lista | `remember(key)` en Screen | Propiedad calculada (`get()`) en ViewModel |
| `scope.launch { search... }` | Evento `onSearch` en Cabecera | Función `buscarAmigos()` en ViewModel |

### Ventajas de este cambio:
1.  **Testeo:** Puedes probar la búsqueda de amigos sin tener que abrir el emulador (haciendo un test unitario del ViewModel).
2.  **Cabecera estúpida:** Tu `CabeceraAmigos` ahora es un componente genérico. No necesita saber qué es un `CaseFacade`, solo sabe que cuando alguien busca, tiene que avisar a través de un callback.
3.  **Persistencia:** Si el usuario minimiza el juego y vuelve, la lista de resultados seguirá ahí exactamente como la dejó.

@Composable
fun TarjetaAmigo(cF: CaseFacade, SEState: SENavHostController, amigo: Usuario, expandido: Boolean, onClick: () -> Unit) {
    // Si te ha invitado, se usa azul claro
    val fondo = if (amigo.haInvitado) color_selected
    else if (amigo.estaOnline) color_secondary
    else color_unselected

    Surface(
        color = fondo,
        modifier = Modifier
            .fillMaxWidth()
            .padding(vertical = 20.dp),
        shadowElevation = 4.dp

            if (expandido) {

-----

Siguiendo con la filosofía de **MVVM**, la función `desplegableOptionAccion` es una candidata perfecta para moverse al **ViewModel**. Actualmente, estás pasando demasiadas cosas (`CaseFacade`, `CoroutineScope`, `SENavHostController`) a una función global, lo cual hace que tu UI sea difícil de mantener y testear.

Aquí tienes cómo reorganizarlo para que quede profesional:

### 1. Mueve la lógica al ViewModel
En lugar de comparar un "String" (que es peligroso porque si cambias una letra deja de funcionar), crea funciones específicas en el ViewModel. El ViewModel ya tiene su propio `viewModelScope`, así que no necesitas pasárselo.

```kotlin
class AmigosViewModel(private val cF: CaseFacade) : ViewModel() {

    // ... (Estados de listas que ya tenías)

    fun invitarAmigo(nombre: String) {
        viewModelScope.launch {
            cF.amigosCase.invitarAmigoLobby(nombre)
            // Aquí podrías actualizar un estado de "Invitación enviada"
        }
    }

    fun unirseAPartida(nombre: String, onSuccess: () -> Unit) {
        viewModelScope.launch {
            cF.amigosCase.unirseAmigoLobby(nombre)
            onSuccess() // Navegamos solo si la llamada fue exitosa
        }
    }

    fun eliminarAmigo(nombre: String, onSuccess: () -> Unit) {
        viewModelScope.launch {
            cF.amigosCase.eliminarAmigo(nombre)
            // Aquí podrías recargar la lista de amigos automáticamente
            onSuccess()
        }
    }

    fun añadirAmigo(nombre: String, onSuccess: () -> Unit) {
        viewModelScope.launch {
            cF.amigosCase.añadirAmigo(nombre)
            onSuccess()
        }
    }
}
```

### 2. Simplifica el Componente `desplegableAmigo`
Ahora tu componente no necesita el `scope` ni el `cF`. Simplemente llama a las funciones del ViewModel.

```kotlin
@Composable
fun desplegableAmigo(
    viewModel: AmigosViewModel, // Pasamos el VM
    SEState: SENavHostController, 
    usuario: Usuario
) {
    Column(...) {
        // ... lógica de colores y lista de acciones ...

        acciones.forEach { (icono, texto, color) ->
            // Usamos un onClick directo en la Surface o Row
            Row(
                modifier = Modifier
                    .fillMaxWidth()
                    .clickable { 
                        // REEMPLAZO de la función gigante por lógica directa
                        when (texto) {
                            "Invitar a la partida" -> viewModel.invitarAmigo(usuario.nombre)
                            "Unirse a la partida" -> viewModel.unirseAPartida(usuario.nombre) {
                                SEState.goTo(Destinos.JUGAR_CREAR)
                            }
                            "Borrar amigo" -> viewModel.eliminarAmigo(usuario.nombre) {
                                SEState.goTo(Destinos.JUGAR_AMIGOS)
                            }
                            "Añadir amigo" -> viewModel.añadirAmigo(usuario.nombre) {
                                SEState.goTo(Destinos.JUGAR_AMIGOS)
                            }
                        }
                    }
                    .padding(vertical = 10.dp),
                verticalAlignment = Alignment.CenterVertically
            ) {
                // ... Icono y Texto ...
            }
        }
    }
}
```

### ¿Por qué este cambio es mejor?

1.  **Seguridad de Hilos**: Al usar `viewModelScope`, si el usuario cierra la pantalla de amigos a mitad de un "Borrar amigo", la operación se completa correctamente en el ViewModel antes de morir, evitando estados inconsistentes.
2.  **Adiós a la función "Basura"**: `desplegableOptionAccion` era lo que llamamos un *God Function* (intentaba hacerlo todo). Ahora cada acción tiene su propio método claro.
3.  **Navegación Controlada**: Al pasar el `onSuccess` (callback) al ViewModel, te aseguras de que la navegación solo ocurra cuando la operación en el servidor/base de datos haya terminado de verdad.
4.  **Menos parámetros**: Tus componentes Composable ahora son mucho más ligeros. No necesitan arrastrar el `CaseFacade` por todos los niveles (Prop Drilling).

**Sugerencia de diseño:** En lugar de usar el texto para el `when`, podrías usar un `enum class AccionAmigo { INVITAR, UNIRSE, BORRAR, AÑADIR }`. Es mucho más seguro porque el compilador te avisará si te equivocas al escribir.
